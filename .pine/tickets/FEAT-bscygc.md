## Scope

KilasFlow already has the hard half of a public API contract and none of the easy half. The hard half is that there is no checked-in specification to drift: `scripts/openapi-spec.mjs` builds a binary, boots it on a reserved free port, polls `/api/v1/ready`, fetches `/api/openapi.json`, asserts the document declares OpenAPI 3.1 and writes it out. Its header states the reason — "The document comes from a real KilasFlow binary rather than a checked-in copy, so a generated client can never drift from the API the server actually serves" — and both `web/` and `sdk/` import that one module. The document is generated by huma from the Go handler types, so it cannot describe an endpoint the server does not serve.

The easy half is absent. Nothing says what `/api/v1` promises. There are 33 operations, RFC 9457 problem responses throughout, structured `WorkflowValidationIssue` payloads on compile failure, an SSE stream with nine named event types and `Last-Event-ID` resume, and no statement anywhere about which of those a consumer may depend on, what may change without warning, or what a breaking change even is here.

`sdk/src/version.ts` gets closest, and it is a doc comment rather than a policy: `SDK_VERSION` follows semver for the package surface, `API_VERSION` is `'v1'` and tracks the URL path, and "a host can upgrade one without the other". `sdk/README.md` repeats it under a `## Versioning` heading. Nothing enforces either statement, nothing bumps either number, and both packages have sat at `0.1.0` since they were written.

Two concrete inconsistencies have to be settled by this ticket because every later p10 ticket inherits them. `sdk/package.json` declares `"license": "MIT"` while the repository `LICENSE` is Apache-2.0 — a discrepancy that becomes a published fact the moment V2-p10-8 runs `npm publish`. And the two drift detectors that would keep the contract honest, `web/scripts/check-api-client.mjs` and `sdk/scripts/check-types.mjs`, are written, correct, and run by nothing; V2-p10-1 wires them, this ticket is what makes them a gate rather than a warning.

## Acceptance criteria

- [ ] A written contract states which parts of `/api/v1` are stable — paths, operation ids, request and response shapes, problem types, SSE event names — and which are explicitly not.
- [ ] The breaking-change policy is written in terms a consumer can check: what forces a new `/api/vN` path, what may ship in a minor release, and what an additive change is permitted to be.
- [ ] The `SDK_VERSION` and `API_VERSION` split moves from a doc comment to an enforced rule, with a stated procedure for bumping each and a check that fails when the package surface changes without one.
- [ ] Both drift detectors are blocking gates rather than advisory scripts, and a handler-type change that is not regenerated fails the build.
- [ ] The licence discrepancy is resolved: `sdk/package.json` and the repository `LICENSE` agree, and the decision and its reason are recorded.
- [ ] The OpenAPI document reports a real version rather than a dirty commit hash, which V2-p10-2 delivers and this ticket asserts as a contract property.
- [ ] It is stated which operations an embed session may reach and which it may not, since `permits()` default-denies and that boundary is part of the public contract, not an implementation detail.
- [ ] A consumer can determine, from published material alone and without reading Go, whether an upgrade will break them.

## Implementation Plan

Write the contract as a document under the docs site's reference section, but land the policy first — V2-p10-9 depends on this decision, not the other way round, so do not wait for a site to exist before deciding what is being promised.

Start from the generated document rather than from intent. Enumerate the 33 operations, their problem types and the nine SSE event names, and mark each stable or unstable deliberately. The instinct is to declare everything stable; resist it for the pieces the roadmap is about to change. `node.Definition` is serialized directly as the `/api/v1/node-types` payload, and p2 adds fields to it in almost every ticket; `workflow.Port` has no JSON tags today so it serializes with capital keys, and V2-p2-8 records that adding tags is a breaking client change. Both facts belong in the contract as declared instability, not discovered breakage.

The versioning rule needs one more distinction than `sdk/README.md` currently draws. `API_VERSION` tracks a URL path and therefore changes almost never; the useful signal for a consumer is which server build they are talking to, which is `info.version` in the document and the `-version` flag on the binary. Say which of the three answers which question, or hosts will pin the wrong one.

The licence question is a decision, not a discovery, and it should be made rather than inherited. Apache-2.0 for the SDK matches the repository and carries an explicit patent grant; MIT is more permissive and is what the manifest already claims. Recommend Apache-2.0 for consistency with the product the SDK exists to serve, and record the reasoning either way — a published package's licence is very hard to change afterwards.

One thing to keep rather than reform: the SDK's deliberate refusal to have an opinion about authentication. `sdk/src/http.ts` documents `headers` as the escape hatch precisely because the shape of a host's credential is not knowable — "inventing one shape would force the others to work around it". V2-p10-6 adds a first-class option on top of that; it must not remove the escape hatch, and the contract should say the escape hatch is supported rather than transitional.
