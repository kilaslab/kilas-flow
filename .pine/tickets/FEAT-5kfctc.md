## Scope

The `mappings` table in `internal/interop/n8n/n8n.go` pins `exportTypeVersion: 2.4` for both `n8n-nodes-base.postgres` (lines 178 to 180) and `n8n-nodes-base.mySql` (181 to 183). Both numbers are stale — n8n serves Postgres at 2.7 and MySQL at 2.5 — and both entries share one converter pair, `sqlToKilas` and `sqlToN8N`, so the two nodes are treated as one node with two names.

That shared pair is where the family's cited import defect lives. `sqlToKilas` at `internal/interop/n8n/parameters.go:541` accepts only `executeQuery`: any other operation returns `map[string]any{"operation": "query"}` with no statement at all — a configured node that is an empty query — plus one diagnostic (lines 544 to 548). `sqlToN8N` at line 570 is the mirror image, writing `"operation": "executeQuery"` and an empty `"options"` map whatever the KilasFlow node held. Once V2-p4-9 and V2-p4-10 register the six operations, every one of them still imports as nothing.

`options.queryReplacement` is reported rather than translated. Lines 556 to 563 emit an Unsupported naming the values and telling the user to retype them into the Parameters field, even though `parameters` at `nodes/database.go:71-74` is exactly the bound array those values belong in, and `boundParameters` at line 276 already accepts a JSON array.

`kilasflow.sqlite` has no mapping entry at all, and the consequence is worse than a lossy export. `byKilasType` at `internal/interop/n8n/n8n.go:200` returns false, so `Export` omits the node entirely at lines 620 to 627; the connection loop then drops every edge through it at 659 to 667 with the generic reason "a connection referenced a node that was not exported and was dropped with it". A three-node workflow leaves as two disconnected nodes and one anonymous diagnostic.

This matters because export is the promise that a customer is not locked in, and it is the half of interoperability nobody tests until they need it. A round trip that silently deletes a node and rewires the graph around it is worse than a refusal, because the resulting file opens in n8n and looks plausible.

## Acceptance criteria

- [x] `n8n-nodes-base.postgres` exports at typeVersion 2.7 and `n8n-nodes-base.mySql` at 2.5, asserted as exact numbers by a fixture rather than as "not 2.4".
- [x] Each n8n SQL operation has its own converter in both directions, and importing a `select`, `insert`, `upsert`, `update` or `deleteTable` node yields a configured node rather than an empty query, proven by one fixture per operation.
- [x] `options.queryReplacement` arrives as the bound `parameters` array with the same values in the same order, and the diagnostic that reported it unsupported no longer appears, proven by a round-trip fixture.
- [~] A replacement value containing a comma survives import as a single parameter, proven by a fixture that asserts the resulting binding element by element.
- [x] Exporting a workflow containing a `kilasflow.sqlite` node preserves the node count and every edge of the source graph, proven by a fixture comparing connections before and after.
- [x] `SupportedMappings()` lists every pair this ticket adds and a test asserts the list, so the interoperability claim stays a written-down, checkable fact.
- [x] Export, import and export again of any SQL node produces byte-identical n8n JSON on the second export, proven by an idempotence fixture.
- [x] The corpus scoreboard's imported, activatable and executable counts are regenerated by hand through `make corpus-baseline` and the new figures recorded in the ticket's work evidence.

## Implementation Plan

Split the converters before touching the version pins. Raising `exportTypeVersion` to 2.7 while `sqlToN8N` still writes `executeQuery` and an empty options map advertises a fidelity the exporter does not have — an n8n instance would read the document as a modern Postgres node and find none of the parameters that version implies. The pins are the last change in this ticket, not the first.

Recommend a dispatch table from the n8n `operation` string to a converter pair, one entry per operation, keyed alongside the dialect so Postgres and MySQL can diverge where their emitted SQL diverges. Reject growing the existing `switch` inside `sqlToKilas`: six operations times two directions times two dialects is twenty-four behaviours, and the current function already demonstrates what happens when one function serves two nodes — a defect in one is a defect in both, invisibly.

Translate `queryReplacement` into `parameters` rather than reporting it. n8n accepts both an array and a comma-joined string in that field, and the array form is a straight copy into the shape `boundParameters` already decodes.

The trap is the string form. Splitting on commas turns a value such as `Smith, John` into two bindings, and when the statement happens to carry two placeholders the query runs — against the wrong data, with no error from the driver, no diagnostic from the importer and a plausible row count. Recommend splitting only when the resulting count matches the statement's placeholder count and emitting a blocking diagnostic naming the ambiguity when it does not, rather than guessing; a refused import the user can fix is strictly better than a silently rebound one.

Tell V2-p1-12's author what this removes. That ticket widens the diagnostic type with a severity and a field name, and the SQL path currently contributes two of its examples — the empty-query report at `internal/interop/n8n/parameters.go:544-548` and the `queryReplacement` report at 556 to 563. Both disappear here. Its severity taxonomy should not be designed around them, and its fixtures should not assert their text.

**How `kilasflow.sqlite` leaves.** Recommend emitting the node under its own type string with its own typeVersion, unmapped, so n8n renders it as an unrecognised node and every edge through it survives — the exact mirror of what `Import` already does with `UnsupportedNodeType` and its capsule at `internal/interop/n8n/n8n.go:295-305`, and a Lossy entry naming the node rather than the anonymous connection message. Reject mapping it to `n8n-nodes-base.noOp`: that turns a database write into a node n8n will happily run as nothing, which is the failure mode this whole ticket exists to remove. What would reopen it is n8n gaining a SQLite node, at which point the entry becomes an ordinary mapping like the other two.

## Work evidence

### Premises that were already false

Every line number the ticket cites is from `nodes/database.go`, the version 1
node, and most of its scope section describes a converter that no longer
exists. `sqlToKilas` and `sqlToN8N` were replaced by `postgresToKilas`,
`postgresToN8N` and two thin MySQL wrappers in `bf2d82e` and `479a9f1`. All six
operations already imported onto their own shape, the schema and table
locators, the `columns` mapper block, `where`, `combineConditions`, `returnAll`
and `limit` already carried, and the acceptance criterion asking for one
fixture per operation was already met by `TestEveryPostgresOperationImportsOntoItsOwnShape`.

The ticket also recommends replacing the `switch` with a per-operation dispatch
table. Rejected: five of the six operations share one parameter surface, and
the whole MySQL divergence is two lines. A dispatch table would be more code
saying less.

### The three silent losses this actually found

**`deleteCommand` defaulted in opposite directions.** n8n's default is
`truncate` — `Postgres/v2/actions/database/deleteTable.operation.ts:25`, and
identically for MySQL — and this node's is `delete`. Import copied the key only
when n8n had stored one and export wrote it only when this node had, so an
absence crossed the boundary and each side read its own default. An n8n delete
node whose author never opened the dropdown meant TRUNCATE and imported as a
row delete; a node authored here and exported meant a row delete and arrived as
a **TRUNCATE**, which empties the table. Both directions now always write the
key: a default never crosses.

**`sort` was dropped with no diagnostic at all.** n8n's select carries a
`sortFixedCollection` (`common.descriptions.ts:302`); nothing read it, neither
v2 node declared a sort property, and `buildSQLStatement` passed `nil` for the
order even though `sqlbuild.Select` has taken `[]Order` and emitted `ORDER BY`
since it was written. An imported `ORDER BY created_at DESC LIMIT 50` returned
an arbitrary fifty rows — output that looks like data rather than like a
defect. Both nodes now declare the collection in n8n's own stored shape and the
builder reads it.

**Export downgraded a node's version.** `Import` preserves n8n's source
typeVersion, but `exportVersion` returned the fixed pin for any mapping that is
not `sharedVersion`, so a workflow authored in n8n at 2.7 round-tripped out at
2.4. Below 2.7 n8n hands DATE and date-array columns back as JS `Date` objects
where this server returns RFC3339 strings, so that is a results change with
nothing in the diff to show for it.

`restartSequences` was dropped too, and is now carried and applied —
`TRUNCATE … RESTART IDENTITY` on PostgreSQL, and declared only there because
MySQL always resets AUTO_INCREMENT and has no keyword for asking.

### Why the version pin could not simply be raised

n8n's `getNodeType` is an exact map lookup with no resolve-down
(`packages/workflow/src/versioned-node-type.ts`), so a typeVersion n8n does not
publish makes it throw `NodeVersionNotFoundError` when the file is opened. The
mapping therefore gained `publishedVersions`, transcribed from
`Postgres.node.ts:19-29` and `MySql.node.ts:19-27` as a Go literal — the
reference checkout is never a build input. Export now writes the pin for a node
sitting at exactly the version this server registers (it was authored here and
has no n8n version to preserve) and the node's own version otherwise, but only
when that version is one n8n publishes.

Setting `sharedVersion` instead would have been wrong: it also arms
`versionIssue`, which emits a **blocking** import diagnostic whenever the
catalogue lacks the exact version — and this server registers V(1) and V(2)
only, deliberately. Every real n8n Postgres import would have been blocked.

### The acceptance criterion that is wrong as written

AC 4 asks that "a replacement value containing a comma survives import as a
single parameter". It cannot, and it should not. n8n's own `stringToArray`
(`Postgres/v2/helpers/utils.ts:46-52`) splits on every comma, filters empty
entries, then trims, with no escape of any kind — so a value containing a comma
was already two values in n8n. Importing it as one would make the workflow run
a different query here than it ran there, which is the opposite of fidelity.

What is implemented is n8n's split reproduced exactly, including the observable
order of filter-then-trim: `"a,,b"` binds two values and `"a, ,b"` binds three,
the middle one empty. The import reports the split so a reader learns that a
comma is a separator on the n8n side. On export, a bound value containing a
comma is left out entirely and named as dropped, rather than joined into a
string that would silently become two values on arrival.

### Two diagnostics corrected

`postgresToKilas` appended an **unconditional** credential `Unsupported` to
every SQL import, including a node with no `credentials` block at all — a false
positive, and a duplicate of the generic `credentialIssue`, which reports the
same thing with a severity and the credential's name. Deleted.

The export used to omit a node n8n has no equivalent of. Every edge touching it
went with it, so a three-node workflow came out as one node and an n8n user saw
a workflow that looked complete and ran almost none of it. Unmapped nodes are
now emitted under their own type: n8n does not recognise the type, shows it as
unknown and refuses to run the workflow, which is the same information
delivered where the user is. `TestExportNamesWhatItCannotCarry` asserted the
omission and was rewritten to assert the node count, the type and the surviving
edge.

### Tests

`internal/interop/n8n/sqlfidelity_test.go` is one hop, not a round trip: from
n8n's JSON to the SQL that actually runs, with the expected fragments taken
from n8n's own source. That is the only shape that can catch an inversion
between the importer's and the exporter's condition maps, because those maps
are each other's inverse and a swap round-trips perfectly while running the
opposite query — the defect fixed in `e8c9bc8`, where `IS NULL` built
`IS NOT NULL`.

- `TestAnImportedConditionBuildsTheSQLN8NWouldHaveRun` — ten conditions, each
  asserting the fragment, the absence of its semantic opposite, and the number
  of bound values. A completeness check against `N8NConditionNamesForTest()`
  fails if an eleventh condition is added without a row.
- `TestAnImportedDeleteCommandBuildsTheVerbN8NWouldHaveRun` — four rows
  including the absent one, which is the case that used to be wrong.
- `TestAnImportedSortBuildsTheOrderItNames` — present and absent.
- `TestImportedQueryReplacementsArriveBound` — element by element on the bound
  parameters, plus n8n's exact split semantics.
- `TestTheSQLNodesExportAtTheVersionTheyMean` — exact numbers, both directions,
  and a check that every version the exporter can emit is one n8n publishes.
- `TestExportingASQLWorkflowTwiceIsIdempotent` — export, import, export,
  `bytes.Equal` on the marshalled document.
- `TestSupportedMappingsAreAdvertisedExplicitly` — the exact 32-pair list,
  replacing a length check and six substrings.
