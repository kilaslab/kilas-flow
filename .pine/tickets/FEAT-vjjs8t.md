## Decisions (2026-09-24)

- **The page is a guide, `guides/code-javascript.md`.** It is the reference for
  one node that people write code in, next to the migration guide. The
  migration guide's long Code-node section moved there; the migration guide
  keeps only what is specific to importing (byte-for-byte source, blocking
  diagnostics, old placeholders run) and links. Safety boundaries keeps the
  worker confinement and links to the page for the limits table, which now
  lives on the page with every `code.javascript_*` key and the fixed bounds.
- **The enumeration is a reviewed list, not a hand-written allowlist in Go.**
  `testdata/surface.txt` is generated by `-update-surface` and compared
  exactly, so any change shows up as a diff a reviewer reads. Array indexes
  are collapsed to `[i]`, a function's untouched `prototype` is not listed,
  and vendored libraries are listed by their root (walked for Go values all
  the same), which keeps it at ~490 reviewable lines.
- **The Go-side checks need an internal test.** Deciding whether an object is
  a reflected Go value, and comparing with the host callbacks by identity,
  needs the VM: `Runner.afterRun` (a test seam like `betweenItems`; it was
  `inspect`) hands the VM to the test after the code ran, and `vm.callbacks`
  keeps the callbacks object for it.
- **The load test is a Go benchmark** in `internal/jsworker`, where the test
  binary is already its own worker, reporting percentiles with
  `b.ReportMetric`; `make js-load` runs it with 400 executions per level and
  prints the load average before and after.

## Security review (2026-09-24)

**Scope.** The JavaScript Code node's runtime (`internal/jsrun`), the worker
processes it runs in (`internal/jsworker`), and what goja and `goja_nodejs`
put in front of a script. **Threat model.** A workflow author writes hostile
JavaScript. They want to reach the host (files, the network, processes, the
server's memory or CPU past the limits), another tenant's data, or a later
run. The worker confinement on Linux (FEAT-21h6xp) is the second line and is
documented in `concepts/safety-boundaries.md`; this review is about the first:
what the engine lets a script touch at all.

Each claim below is held by a test that fails if it stops being true.

### 1. Prototype pollution stays in one execution, and one tenant

Every execution gets a new goja VM, thrown away afterwards; the only thing
shared between VMs is compiled `*goja.Program`s, which running cannot change.
So a script may rewrite any built-in, and that is its own business.

- `TestPrototypePollutionIsConfinedToOneExecution` (jsrun) pollutes 22 things
  at once: `Object`/`Array`/`Function`/`String` prototypes, `JSON.parse` and
  `stringify`, `Promise.prototype.then`, `Math.random`, `Date.now`, a global,
  the `Symbol.for` registry, `Buffer.prototype` and `Buffer.from`, `URL`, the
  module objects of lodash, `crypto` and `util`, Luxon's
  `Settings.defaultZone`, `Intl.NumberFormat`, `console.log`, and freezes
  `Object.prototype`. The next execution, in either mode and under another
  workflow, sees none of it and computes correctly with all of it.
- `TestOneTenantsJobCannotReachTheNextOnTheSameWorker` (jsworker) proves the
  same across the process boundary: one worker (`MaxConcurrent: 1`, asserted
  started once) runs tenant A's polluting job and then tenant B's, and B sees
  nothing of A's, its `$env` and `$workflow` included.
- Within one execution, pollution cannot change what the *server* accepts.
  `TestPollutionCannotMakeAResultNameAnotherFile` tries six ways (an
  inherited `binary`, a getter on `Object.prototype`, replaced
  `JSON.stringify`, `toJSON` on `Array.prototype` and `Object.prototype`, and
  editing an input file's id): no result ever carries a file the node was not
  given, because the runtime captured its built-ins before user code and the
  server decodes the returned JSON itself against the input's files. A run
  may fail (a getter-only `binary` breaks the runtime's strict-mode
  assignment), but only as the code's own error, never an engine fault.

### 2. Host bindings are plain functions and plain data

- **Natives** (hash, cipher, codec, Intl…) take plain values only (nil, bool,
  number, string, bytes, lists, maps), check every argument against a per-call
  bound before working, and return plain values; a structured result crosses
  as JSON, so a script never holds a live Go object (`natives.go`,
  `vm.toJS`).
- **Host callbacks** (`node`, `pair`, `console`, `call`, `staticData`,
  `native`, `library`, the timers) are handed to the runtime's closure and to
  the modules' `kit`, never set as globals.
  `TestNoScriptReachesTheHostCallbacks` walks everything a script can reach
  and compares every object with every callback by identity, and looks for
  anything shaped like the kit. Its second pass first replaces every method of
  ~30 built-in objects and prototypes with one that keeps its receiver and
  arguments, then drives every module (console, `$()`, Buffer, crypto
  including GCM, Intl, Luxon, lodash, URL, timers, static data, all three
  helpers), and walks what was kept as well. Mutation check: planting
  `[host.console].indexOf(0)` in `runtime.js` makes it fail, naming the path.
- **Found: BUG-h6tj4e (fixed here).** `goja_nodejs` hands two Go values to the
  VM by reflection, and goja exposed their exported methods:
  `Buffer[Symbol(api)]` (its `*buffer.Buffer`, with `WrapBytes` and
  `RequiredBufferArgument`) and every `URL` (its `*nodeURL`, with `String`).
  `WrapBytes({ length: 2 ** 27 })` held a core 6.5 s past a 200 ms limit, in
  one call nothing interrupts, around every per-call bound. Every VM now sets a
  goja field-name mapper that hides all Go fields and methods; goja_nodejs
  still finds its values by exporting them, which the mapper does not touch.
  `TestNoGoFieldOrMethodIsReachable` fails on any reachable Go value with a
  member; `TestGoHandlesOfferNothingToCall` pins the visible side.
- **The enumeration.** `TestTheScriptSurfaceIsTheReviewedOne` walks, breadth
  first in a fixed order, the global object, `this`, the arguments, and an
  instance of everything a script can be handed or construct (items,
  `$input`, `$()` views, static data, URL and its iterator, Buffer, text
  codecs, DOMException, every crypto object, every Intl object, the modules,
  errors from natives and from goja_nodejs, helper results, a timer),
  following prototypes, accessors and symbol-keyed properties. What it finds
  beyond a bare goja VM must equal `internal/jsrun/testdata/surface.txt`
  (about 490 lines); a new, changed or vanished property fails the test until
  the list is rewritten with `-update-surface` and the diff reviewed. The
  vendored libraries are walked for Go values but listed by their root.
  Reviewed entries worth a note: a global `_` holding `undefined` (lodash's
  `noConflict` leaves the property behind; harmless); crypto objects keep
  their state under `Symbol(kilasflow.crypto)`, which a script can edit, but
  that state only ever reaches natives that validate it; `TextDecoder`'s
  `_encoding`/`_fatal`/`_ignoreBOM` and a timer's `_timerId` are plain JS
  fields; `Buffer[Symbol(api)]` is now an opaque handle.

### 3. `eval` and `new Function` cannot reach the host

They stay enabled, as in n8n.
`TestCodeCompiledAtRunTimeReachesNothingTheBodyCannot` compiles code through
indirect `eval`, `new Function`, `Function.prototype.constructor`, a
generator's constructor, a host function's constructor (`$input.all`,
`Buffer.from`) and an error's constructor chain: each gets the same
`globalThis` and the same `require`, and no `process`, `module`, `exports`,
`global`, `__dirname`, `Deno`, `Bun`, `WebAssembly`, `fetch`,
`XMLHttpRequest` or `SharedArrayBuffer`; a `require('child_process')` from
`new Function` gets the refusal sentence. A direct `eval` sees the body's own
scope. Runtime-compiled code never reads a source map from disk
(`TestASourceMapCommentNeverReadsTheFilesystem`, existing).

- `Error.prepareStackTrace` is never called and `Error.captureStackTrace`
  does not exist; every `stack` is a string, so no call-site object ever
  hands out a receiver or a function (`TestStackTracesAreTextNeverFrames`).
- Symbol tricks: symbol-keyed properties are part of the walk (that is how
  `Symbol(api)` was found). goja makes `Object.prototype`'s prototype
  immutable, so a Proxy cannot be slipped under every object to observe the
  runtime's property reads (probed by hand).
- Proxies on host objects: `TestAProxyHandedToTheHostIsTreatedAsData` hands a
  transparent, a throwing and a revoked Proxy to 22 host entry points (Buffer,
  crypto, `$()`, static data, Intl, URL, text codecs, `structuredClone`,
  `util.inspect`, console, `$input`, timers, all three helpers). Each returns
  or throws (or rejects) an ordinary JavaScript error the code can catch,
  never a Go error or an engine fault. A built-in that reads a length refuses
  a Proxy by design, since its traps would run once per element inside one
  uninterruptible call.

### 4. A hostile worker is treated as hostile

Already tested in `internal/jsworker`, not duplicated: the `lyingWorker` modes
(`stale`, `unknownfile`, `flood`, `calls`, `bigcall`, `badhelper`,
`staticflood`, `staticunused`, `bigdone`) behind
`TestTheServerTrustsAWorkerOnlyAsFarAsItsCodeCouldGo`,
`TestAWorkerThatOverstepsTheHelpersIsRetired`,
`TestAWorkerRefusesARepliesItDidNotAskFor` and
`TestAFrameLargerThanItsLimitIsRefusedBeforeItIsRead`.

### 5. Probes that found nothing

A sparse array of length 2^30 handed to `JSON.stringify`, `toString`,
`structuredClone`, `TextDecoder`, `util.inspect`, `console.log`, `Object.keys`,
a spread into `String.fromCharCode`, `crypto` `update`, `URLSearchParams` and
lodash's `cloneDeep`, and array-likes of 2^27 handed to `Buffer.from`,
`Buffer.concat`, `Buffer.alloc`: each was stopped by a per-call `RangeError`
or by the clock within the limit.

### Residual risks (unchanged, documented)

- The per-call bounds are a denylist: one uninterruptible built-in call may
  still overrun. In the server that costs a worker, which the pool kills at
  twice the limit plus 5 s, and on Linux its address-space limit bounds the
  memory.
- There is no per-execution memory accounting; the heap ceiling is per worker.
- `err.stack` names the runtime's own frames (`kilasflow:runtime:<line>`).
  The runtime is open source, so this discloses nothing.
- While here: `code.javascript_heap_ceiling_mb`'s description said a worker's
  address-space limit was four times the ceiling plus 1 GiB; the code
  (`addressSpace`) and the safety-boundaries page say plus 3 GiB. The
  description is corrected and the reference regenerated.

## Load test (2026-09-24)

`BenchmarkCodeNodeUnderLoad` (`internal/jsworker/load_test.go`), run by
`make js-load`: Code-node executions through the real worker pool
(`jsworker.Pool`, default command, so the test binary is its own worker), the
pool sized as the server sizes it by default (one worker per CPU, here 10),
workers warmed first. Each execution is timed from `Pool.Run` to its decoded
items: preparing the job, queueing for a worker, the run, decoding. 400
executions per row (`-benchtime 400x`). Bodies: `return items` over 1 item,
and a transform over 1,000 order-shaped items (trim, upper-case, arithmetic,
filter a list, format a date).

**Machine:** Apple M4, 10 cores (4 performance, 6 efficiency), 24 GiB,
macOS 27.0 (26A428), Go 1.27.1 darwin/arm64, no worker confinement (not Linux).
Shared with other agents' work.

**Run 2 (the one on the docs page).** Load average at start 1.93 / 2.48 / 2.89,
at end 5.38 / 3.20 / 3.14 (the end includes the benchmark's own 10 workers).

| Body | Concurrency | p50 | p95 | p99 | execs/s |
|---|---:|---:|---:|---:|---:|
| trivial | 1 | 0.80 ms | 0.97 ms | 1.01 ms | 1331 |
| trivial | 4 | 1.15 ms | 1.69 ms | 1.86 ms | 3516 |
| trivial | 10 | 2.18 ms | 3.52 ms | 3.99 ms | 4540 |
| trivial | 40 | 8.62 ms | 10.67 ms | 11.60 ms | 4527 |
| transform1000 | 1 | 18.73 ms | 19.70 ms | 20.96 ms | 53 |
| transform1000 | 4 | 24.44 ms | 27.49 ms | 44.20 ms | 160 |
| transform1000 | 10 | 43.28 ms | 61.60 ms | 84.27 ms | 219 |
| transform1000 | 40 | 177.4 ms | 204.0 ms | 226.2 ms | 219 |

**Run 1**, minutes earlier. Load at start 1.97 / 2.57 / 2.98, at end
3.32 / 2.82 / 3.06. Trivial: p99 1.02 / 1.72 / 3.85 / 10.84 ms at 1 / 4 / 10 /
40, and 1318 / 3647 / 4698 / 4540 execs/s. Transform: p99 34.6 / 74.9 / 83.8 /
221.7 ms, and 51 / 118 / 217 / 218 execs/s. The concurrency-4 transform
row is the noisiest (p95 56.9 ms against 27.5 ms in run 2): another agent's
work was competing for the performance cores.

**Reading.** A trivial run costs about 0.8 ms end to end, most of it the
round trip to a warm worker. A 1,000-item transform takes about 19 ms and
scales to ~220 executions/s at 10 workers, where the CPUs are saturated;
beyond one execution per CPU, throughput holds and latency grows with the
queue (p99 grows about linearly with the queue length), and nothing failed.
The 10-core number is under the 4+6 split, so the efficiency cores slow the
10-at-once rows.
