# Description

Several CPU-heavy tests in `internal/jsrun` run a script under the shipped
`DefaultLimits()` (10 s of user time) and fail with the time limit when the
machine is heavily loaded under `-race` (load average 20–50, other test
suites running in parallel). Seen during EPIC-tjnr1z's parallel work, on
clean `main` as well as on branches:

- `TestBuiltinsThatAmplifyTheirInputAreBounded`
- `TestConsoleJSONPlaceholderMarksCyclesAndTextTooLargeToBuild`
- `TestDeeplyNestedArraysCannotHoldTheCPU` (guards_test.go)
- `TestEveryCurrencyHasNodesSymbolsAndDigits` (intl_test.go)
- `TestTheHeapWatchdogStopsARunawayAllocation` (once)

Each passes when run alone. The user-time clock is CPU-agnostic wall time
between VM entries, so a starved CPU is charged to the script.

# Acceptance Criteria
- [x] Each test proves what it proves without depending on the machine being
      idle: shrink the work to what the assertion needs, or measure the bound
      the test is about (a per-call element cap, a placeholder) rather than
      "finishes within the 10 s limit".
- [x] Do not widen the limit (see .pine/memory/code-node.md: a test-only limit
      is how BUG-9s3htg went unnoticed).
- [x] `go test -race -count=3 ./internal/jsrun/` passes with another `-race`
      suite running beside it.

# Notes

## Plan
For each listed test, identify the property it proves and shrink the JS it
runs (and drop any wall-clock assertion redundant with that property) so the
work stays cheap regardless of CPU contention, instead of widening any limit.
Profiled each candidate script with a throwaway benchmark harness (removed
before commit) to find which lines actually cost real time under `-race`,
rather than guessing.

## Root causes found (idle timings, `-race`, before fixes)
- `refusedQuickly`'s own `elapsed > ...` wall-clock assertion was an
  additional, unnecessary failure surface on top of the run's own 10 s
  `DefaultLimits().Timeout` — removed; the message check alone already
  catches a bound that silently stopped checking up front.
- goja's `String.prototype.repeat` (dop251/goja `builtin_string.go`,
  `stringproto_repeat`) writes its ASCII fast path one `sb.WriteString(a)`
  call per repetition — for `'x'.repeat(2 ** 24)` that is 16.7M tiny writes,
  ~836 ms alone under `-race`, ~3x that inside a loop. Several tests built a
  "legal but large" fixture this way. Fixed by building the same string with
  doubling (`s = s + s`, 24-26 steps: one bulk copy per step, ~50 ms) — a
  behaviour-preserving swap, not a scope change.
- `JSON.stringify` genuinely has to escape whatever content passes the
  incremental `characters()` check before the bound trips (~58 ms/MiB under
  `-race`); at the real `MaxCharactersPerCall` (32 MiB) this floors around
  1.6-2.4 s however the array is chunked (measured 4, 8, 10, 20, 40, 64, 150,
  600 elements — all converged, because total escaped bytes is what's fixed,
  not element count). `TestBuiltinsThatAmplifyTheirInputAreBounded`'s
  "one large value serialized many times" case keeps this real cost (it is
  the property under test) but now builds its base string cheaply.
  `TestConsoleJSONPlaceholderMarksCyclesAndTextTooLargeToBuild` doesn't need
  array-repetition amplification (its own doc comment: "a value too large to
  write as JSON at all") — switched to one over-the-bound string, which the
  root-level `jsonSize` check refuses before any escaping (idle: 4.7s → 23-75
  ms).
- `Array(N).fill(x).join('')` / `.toLocaleString()` have no glue to
  pre-check, so they total each element incrementally; with N=2**20 tiny
  elements that is ~32,768 loop iterations before crossing the bound, costly
  under `-race`. Rebuilt with a short array (40) of doubled, larger elements:
  same number of bytes crossed, far fewer iterations (idle: ~1-1.2s → ~8ms
  each).
- `String.prototype.concat`'s bound sums argument lengths *before* calling
  the native concat, so it never copies anything once the sum is exceeded.
  Swapped a big-base two-argument call for a small base spread over many
  arguments (idle: ~810 ms → ~7-18 ms).
- `TestDeeplyNestedArraysCannotHoldTheCPU` built 500,000 nested arrays to
  trip `MaxCallDepth` (10,000): the recursive `String()` call can't get past
  10,000 either way, so the extra 490,000 levels of building bought nothing.
  Shrunk the loop to 20,000 (2x the limit, comfortable margin) and dropped
  the test's own 5s wall-clock assertion (idle: ~1.0-1.5s → ~0.2-0.3s).
- `TestTheHeapWatchdogStopsARunawayAllocation` already avoided the repeat
  pitfall (fixed earlier in FEAT-7q13t6) but still grew its hoard via 1,536
  string concatenations of a 64 KiB chunk. Switched to `new Uint8Array(8 <<
  20)` pushes (native bulk allocation, not built up character by character)
  so the same ceiling is crossed in 8 steps; kept it a genuine growing loop,
  not a single allocation. Idle timings were already low (33-83ms); this
  mainly reduces how many VM re-entries (and thus how many chances for a
  starved scheduler to stretch the charged time) the loop needs.
- `TestEveryCurrencyHasNodesSymbolsAndDigits` (intl_test.go) was already
  chunked to 4 locales per run on `main`, prior to this ticket. Benchmarked
  the real golden data directly: the unchunked 162-currency `digits` call is
  112 ms, and the worst 4-locale symbols chunk is 823 ms — both far inside
  the 10 s per-run budget, so this test needed no further change.

## Verification
- `go build ./...`, `go vet ./...`: clean.
- `go test ./internal/jsrun/...`: ok.
- `go test -race -count=3 -v -run '<the five tests>' ./internal/jsrun/`,
  three separate times, each time with a genuinely concurrent, uncached
  `go test -race -count=1 ./nodes/...` running beside it (plus, unplanned but
  representative, other agents' own `go test ./...` / `go test
  ./internal/jsrun/corpus` processes already running on the same machine
  throughout): all three iterations of all five tests PASS every time.
- `go test -race -count=3 ./internal/jsrun/...` (package-level, same
  concurrent `./nodes/...` load): ok, 123.6s.
- `go test -race -count=1 ./nodes/...` alongside it: ok, 133.4s.
