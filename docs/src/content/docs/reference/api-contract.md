This page is the public contract for the KilasFlow HTTP API. It states which
parts of `/api/v1` a consumer may depend on, which parts may move without
warning, what counts as a breaking change, and how versions, licences, and
embed boundaries are enforced rather than merely documented.

Until the first tagged release, everything below is a promise about the future,
not a description of the present: with no release to pin, anything built
against the API today should expect it to move. From the first release tag on,
this page binds.

## Where the contract lives

There is no checked-in specification to drift. `scripts/openapi-spec.mjs`
builds a real binary, boots it on a reserved free port, polls
`/api/v1/ready`, fetches `/api/openapi.json`, asserts the document declares
OpenAPI 3.1, and writes it out. Both the web app (`web/scripts/`) and the
host SDK (`sdk/scripts/`) import that one module, and the document itself is
generated by huma from the Go handler types — so it cannot describe an
endpoint the server does not serve.

Consequences:

- A running server's `/docs` page is authoritative for the instance you are
  talking to. This site is authoritative for the current release. The two do
  not compete.
- The raw document is at `/api/openapi.json` (also `.yaml`, plus
  `/api/openapi-3.0.json` and `.yaml` for tools that cannot yet read 3.1).
- To re-enumerate the operation surface from source instead of trusting this
  page, run `grep -rn 'OperationID' internal/api/handlers/` — every operation
  below appears there exactly once.

## What is stable, and what is explicitly not

**Stable.** Request and response envelopes, field names and types, success
status codes, operation ids, problem shapes ([Errors](#errors)), and SSE
event names ([Events](#events)). A field that exists today keeps its name,
its type, and its meaning within `/api/v1`.

**Explicitly unstable.** Two payloads are excepted deliberately — the
instinct is to declare everything stable, and these two are why that instinct
is wrong:

- `GET /node-types` returns `node.Definition` serialized directly. The
  roadmap adds fields to it in almost every milestone, so new **optional**
  fields may appear in any minor release. Consumers MUST ignore unknown
  fields on this payload.
- `workflow.Port` objects appear inside definitions and workflow documents.
  They serialize today with lowercase keys (`name`, `kind`,
  `displayName`, `required`, `maxConnections`, `allowedNodeTypes`), and new
  optional keys may join them the same way. Consumers MUST NOT reject a port
  object for carrying keys they do not recognise.

**Additive means additive.** A new operation, a new optional request field, a
new optional response field, a new SSE event name, or a new problem-detail
field may ship in any minor release and MUST NOT break a consumer that
ignores unknown fields and unknown event names. Anything else — removing or
renaming a path, operation id, or field; changing a field's type or meaning;
changing a documented success status — is breaking (see below).

## Breaking changes

A breaking change is one a consumer can detect from published material alone,
without reading Go:

- **New `/api/vN` path** is forced by: removing or renaming an operation
  path or operation id; removing a request or response field; changing an
  existing field's type or semantics; changing a documented success status
  code; removing an SSE event name; or withdrawing `Last-Event-ID` resume.
  The old path keeps serving through a documented migration window.
- **Minor release** may carry: new operations, new optional fields, new SSE
  event names, new problem-detail fields, and new instability declarations
  like the two above.
- **Never breaking**: adding an instability declaration that narrows a
  promise is itself a contract change and is announced as one — instability
  is declared here, never discovered in a diff.

To decide whether an upgrade breaks you: diff the generated OpenAPI document
between the two releases (`info.version` tells you which builds you are
comparing), check the SDK changelog for a major bump, and apply the rules
above. If none fires, the upgrade is safe.

## Errors

Every non-success response is an RFC 9457 problem document
(`application/problem+json`) with `title`, `status`, and optional `detail`,
`instance`, and `errors`. The shape is stable; the human-readable strings
inside it are not — never match on `detail` text.

One declared failure carries a member of its own: when a datastore migration is
outstanding, `GET /api/v1/ready` answers `503` with the same `datastores` block
its `200` body carries (see [System](/reference/api/system/)). Its two other
`503`s — an unreachable database, and a fleet status that cannot be read —
carry no block, because neither state can read the catalogue. The spread a
monitor needs is therefore readable in exactly the state that reports a
migration outstanding, instead of only while readiness is green, and without
parsing `detail`. Extension members are additive, so a consumer that ignores
unknown members is unaffected.

Workflow compile failure is structured: a `422` whose error details carry a
`WorkflowValidationIssue` value with `code`, `nodeId`, and `connectionId`,
so a client can map failures back to graph elements without parsing a
message. Draft validation failure is likewise a `422` with a `body`-located
detail. The `code` vocabulary grows additively; unknown codes MUST be
rendered generically, keyed off `nodeId` when present.

## Idempotency

Three operations — `run-workflow`, `insert-datastore-row` and
`upsert-datastore-row` — accept an optional `Idempotency-Key` request header.
The header, the `Idempotent-Replayed` and `Retry-After` response headers, the
two `409` conflict codes (`idempotency_key_reused`, `idempotency_key_in_flight`,
carried as `errors[0].value.code`) and the retention config key
(`idempotency.retention`) are **stable** contract. Adding an optional request
header is additive under the rules above; withdrawing the header, renaming a
code, or changing what a replay returns is breaking.

The guarantees and, just as importantly, the gaps — a failed request frees its
key, a run is not crash-atomic, the in-flight lease is two minutes — are written
out in [Idempotent requests](/guides/idempotency/). A consumer should read that
page before relying on the header, because it is the only place the boundaries
are stated.

## Events

`GET /api/v1/executions/{id}/events` is a server-sent event stream with nine
named event types. The names are **stable**:

`execution.started`, `execution.completed`, `execution.failed`,
`execution.cancelled`, `node.started`, `node.output`, `node.completed`,
`node.failed`, `workflow.saved`.

Delivery promises: each event carries a monotonic numeric `id`; a
reconnecting client resends it as `Last-Event-ID` (or `?from=` where a header
cannot be set) and resumes instead of restarting; the server closes the
stream after a terminal event (`execution.completed`, `execution.failed`,
`execution.cancelled`), so a client MUST stop reconnecting then. Event `data`
is redacted on publish — a subscriber can never see credential material even
if a node returned it. New event types may be added in a minor release;
consumers MUST ignore names they do not recognise.

## Versioning: three numbers, three questions

| Number | Lives in | Answers | Changes |
| --- | --- | --- | --- |
| `SDK_VERSION` | `sdk/src/version.ts`, mirrored in `sdk/package.json` | Which package surface is this host built against? | Semver: major on breaking SDK change, minor on additive surface, patch on fixes. |
| `API_VERSION` | `sdk/src/version.ts` (`'v1'`), tracks the URL path | Which path prefix does this SDK speak? | Almost never — only when a new `/api/vN` path ships. |
| `info.version` / `-version` | OpenAPI document, binary flag | Which server build am I talking to? | Every build. This is the useful signal — pin this, not the other two. |

The SDK and the API upgrade independently: a host can take a new SDK against
the old path, or point an old SDK at a newer server within the same `v1`,
and both directions are supported.

**Bump procedure.** Changing the SDK's exported surface requires bumping
`SDK_VERSION` and `sdk/package.json` together — the two MUST agree, and `make
sdk-version-check` (run in CI) fails the build when they do not. Bumping
`API_VERSION` requires a new served path prefix and the migration window
described above; it MUST NOT move for anything less. Release builds report a
real version in `info.version` and `-version` (tag → build flag → server,
which passes it into the OpenAPI document); untagged development builds
report a commit hash instead, and consumers MUST NOT parse that hash —
treat any non-semver `info.version` as "unreleased".

## Drift gates

Three detectors keep the contract honest, and all are blocking — a
handler-type change that is not regenerated fails the build:

| Detector | Regenerates | Fails when | Fix |
| --- | --- | --- | --- |
| `web/scripts/check-api-client.mjs` | `web/src/lib/api/generated/` | Committed web client differs from a freshly built binary's document | `pnpm generate:api` in `web/` |
| `sdk/scripts/check-types.mjs` | `sdk/src/generated/models.ts` | Committed SDK types differ from a freshly built binary's document | `pnpm generate:types` in `sdk/` |
| `scripts/generate-api-reference.mjs --check` | `docs/src/content/docs/reference/api.md` and `docs/src/content/docs/reference/api/` | Committed reference pages differ from a freshly built binary's document | `node scripts/generate-api-reference.mjs` |

All three build and boot a real binary via `scripts/openapi-spec.mjs`, so the
spec can never be a checked-in copy that fell behind. In the Makefile they
are `make generate-api-check`, `make generate-types-check`, and
`make generate-api-reference-check`; in CI they are the `drift` job, which
runs on every pull request alongside `make sdk-version-check` in the `sdk`
job.

## Authentication: the escape hatch is the contract

The SDK holds no opinion about credentials. `headers` on the transport is a
plain record where a host puts whatever its deployment authenticates —
bearer token, gateway header, signed proxy — because the shape of a host's
credential is not knowable, and inventing one shape would force the others
to work around it. Later tickets may add first-class options on top, but
they MUST NOT remove the escape hatch: `headers` is supported, not
transitional.

## Embed boundary

An embed session is confined to one workflow and its executions; everything
else is refused by default rather than enumerated as forbidden. That
default-deny boundary is part of the public contract:

| Request | Verdict |
| --- | --- |
| `GET /node-types/**` (catalogue, icons, load-options, load-schema) | Allow with `workflow:read` — the catalogue is narrowed to the session's own tenant; load-options is additionally bounded to the session's workflow by the handler |
| `GET /credentials` (list; values are never returned) | Allow with `workflow:read` — names are needed to render a credential picker |
| `GET /workflows/{id}` where `{id}` is the session's workflow | Allow with `workflow:read` |
| `PUT` (and other writes) to the session's workflow, except below | Allow with `workflow:write` |
| `POST /workflows/{id}/run` on the session's workflow | Allow with `workflow:run` |
| `GET /executions?workflowId={session workflow}` | Allow with `workflow:read` — the query MUST name the session's workflow |
| `/executions/{id}/**` | Allow with `workflow:read` — ownership is checked in the handler, which alone can know which workflow an execution belongs to |
| `POST /workflows/import` | Deny — importing creates a new workflow, outside any session's single-workflow authority |
| `POST /workflows/{id}/activate`, `/deactivate` | Deny — activation publishes a deployment-wide endpoint; an owner action, not an embed one |
| `DELETE /workflows/{id}` | Deny |
| Any `/workflows/{other-id}/**` | Deny — scoped to a different workflow |
| `GET /workflows` (list), `POST /embed-sessions`, schedules, credential writes, credential-type endpoints | Deny — none belongs to an embedded editor |

A request without a token passes through untouched: the internal dashboard
is unaffected. A request *with* one is confined as above, so a token that
leaked out of an iframe is useless for anything but the one workflow it was
minted for.

## Licence

The SDK is published under **Apache-2.0**, matching the repository root
`LICENSE`. The manifest previously claimed MIT; that was an accident of
authorship, not a decision. Apache-2.0 is recommended because it matches the
product the SDK exists to serve — one licence for the whole project — and
because it carries an explicit patent grant, which matters for a package
hosts embed in their own products. A published package's licence is very
hard to change afterwards, so this is recorded here and enforced by
`make sdk-version-check`: the SDK ships under Apache-2.0, full stop.
